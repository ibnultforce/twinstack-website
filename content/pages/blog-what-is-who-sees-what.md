            <article>
                <p class="imp-text-xl imp-text-slate-600 imp-font-medium imp-mb-8">
                    A free, native, read-only Salesforce app that answers the access question in the direction it is actually asked.
                </p>
                <div class="imp-border-l-4 imp-border-brand-500 imp-bg-brand-50 imp-p-5 imp-rounded-r-lg imp-mb-8">
                    <p class="imp-mb-0 imp-text-brand-900"><strong>Short answer:</strong> <a href="/products/who-sees-what.html">Who Sees What</a> is a free, 100% native, read-only Salesforce managed package. Pick any user, and it shows every app, object, field and record they can access, plus the exact profile, permission set or sharing rule responsible for each grant. It cannot change anything, which is what makes it safe to install in production.</p>
                </div>
                <h2 id="what-is-it">What is it?</h2>
                <p>It is a permission inspector that starts from the person, not the configuration.</p>
                <p>
                    Standard Salesforce Setup is organised around profiles, permission sets, permission set groups, role hierarchy, sharing rules and manual shares. Each of those screens tells you what a rule does. None of them tell you what a person can actually do, because access is the sum of all six, evaluated together. The <a href="/blog/salesforce-object-field-record-access.html">three layers these six sources feed into</a> are worth understanding separately.
                </p>
                <p>
                    Who Sees What inverts the direction. You pick a user. It resolves everything that applies to them, across every layer, into one screen.
                </p>
                <h2 id="why-does-it-exist">Why does it exist?</h2>
                <p>
                    Because the most common access question in Salesforce administration is asked backwards from how the platform is built.
                </p>
                <p>
                    Someone asks "why can this user see that record?" Setup makes you answer it by opening the user's profile, then their permission sets, then their permission set groups, then the role hierarchy, then sharing rules, then manual shares, checking each one for a relevant grant. Object access, field-level security and record visibility live on different screens entirely.
                </p>
                <p>
                    That reconstruction takes real time. Admins report it commonly taking thirty minutes or more for a single user on a single object, and that is when you already suspect where the access came from. When you don't, it takes longer.
                </p>
                <p>
                    Who Sees What exists to collapse that reconstruction into a lookup. There is a longer account of <a href="/blog/why-salesforce-access-questions-take-so-long.html">why that reconstruction eats an afternoon</a>.
                </p>
                <h2 id="how-does-it-work">How does it work?</h2>
                <ul>
                    <li>Pick any user in your org. No configuration, no setup screen to define first.</li>
                    <li>Optionally narrow to a specific app, or look at everything.</li>
                    <li>See every object, field and record they can reach, with the exact profile, permission set or sharing rule that granted each one.</li>
                </ul>
                <p>
                    Because it only reads permission metadata and does not touch the Salesforce data model itself, there is nothing to configure before the first result. Install it, pick a name, read the answer.
                </p>
                <img src="https://res.cloudinary.com/du42kbmmn/image/upload/w_800,f_auto,q_auto/v1789469066/wsw_1.2_ti2sjz.png" alt="Object, field and record access for a selected user, each row showing the profile, permission set or sharing rule that granted it" width="800" height="450" loading="lazy" class="imp-zoom-image imp-w-full imp-rounded-xl imp-shadow-lg imp-mb-4">
                <p class="imp-text-sm imp-text-slate-500 imp-italic">Every access is shown next to the rule that granted it, so the answer and its cause arrive together.</p>
                <h2 id="where-does-the-data-come-from">Where does the access data come from?</h2>
                <p>
                    Entirely from your own org. Who Sees What queries Salesforce's own permission and sharing metadata: profiles, permission sets, permission set groups, role hierarchy, sharing rules and manual shares. Nothing is transmitted anywhere else, and there is no external service in the picture at all.
                </p>
                <p>
                    That is also why it can be read-only with no loss of function. Every answer it gives is a resolution of rules that already exist in your org; it never needs to write anything to produce that answer.
                </p>
                <h2 id="who-is-it-for">Who is it for?</h2>
                <p>
                    Anyone who has to answer "what can this person do" and currently has to prove it by hand: admins troubleshooting a specific complaint, security and compliance reviewers running an access review, IT and people ops confirming onboarding and offboarding, consultants documenting an org during a handover, and anyone cleaning up permission set sprawl.
                </p>
                <h2 id="which-products">Which Salesforce products does it work with?</h2>
                <p>
                    Sales Cloud, Service Cloud, Data Cloud and Nonprofit Cloud, on nearly every edition, including orgs that use Person Accounts. Because it reads permission metadata rather than depending on a particular object model, it does not care which cloud your org runs.
                </p>
                <h2 id="what-does-it-cost">What does it cost?</h2>
                <p>
                    Nothing. Free, with no user cap, no usage tier, and no feature held back for a paid version. There is one version of the app. The same is true of <a href="/blog/what-is-google-form-auto-sync.html">Google Form Auto Sync</a>, our other free app on the AppExchange.
                </p>
                <h2 id="is-it-secure">Is it secure?</h2>
                <p>
                    This is the question worth spending the most time on, because it is unusual for a tool in this category to be genuinely unable to cause harm.
                </p>
                <p>
                    <strong>No write operations, anywhere.</strong> Nothing about a profile, permission set, role or sharing rule can be modified from inside the app. It cannot grant access, revoke access, or touch a permission.
                </p>
                <p>
                    <strong>Nothing leaves the org.</strong> It runs entirely inside Salesforce. Your permission model is never sent to an external service for analysis.
                </p>
                <p>
                    <strong>Because it cannot change anything, it can be shared more widely than Setup access.</strong> A security reviewer, an auditor, or a new admin can be given access to Who Sees What without being given access to modify permissions.
                </p>
                <p>
                    That last point matters more than it first appears. Most permission-inspection needs get solved today by temporarily granting someone Setup access so they can look around, which is itself a permission risk. A read-only tool removes that trade-off entirely.
                </p>
                <h2 id="when-not-to-use-it">When should you not use it?</h2>
                <p>
                    <strong>You need to change access, not just see it.</strong> Who Sees What tells you what is granting an access and where to go fix it. It does not fix it for you.
                </p>
                <p>
                    <strong>You need a scheduled, automated compliance report emailed to someone weekly.</strong> Who Sees What is an interactive lookup tool, not a reporting or alerting platform.
                </p>
                <h2 id="how-long">How long does it take to get an answer?</h2>
                <p>
                    Once installed, seconds per user. There is no setup phase, no configuration screen, and no data to import. You install the package, open the app, and search for a name.
                </p>
