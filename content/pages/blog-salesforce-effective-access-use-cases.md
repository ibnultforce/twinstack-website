                <p class="imp-text-xl imp-text-slate-600 imp-font-medium imp-mb-8">
                    The same underlying question, asked in seven different contexts.
                </p>
                <div class="imp-border-l-4 imp-border-brand-500 imp-bg-brand-50 imp-p-5 imp-rounded-r-lg imp-mb-8">
                    <p class="imp-mb-0 imp-text-brand-900"><strong>Short answer:</strong> A user reports missing access, a user has access they should not, a scheduled review, onboarding, offboarding, permission set cleanup, and a consulting handover all reduce to the same question: for this person, what can they access, and what specifically grants it.</p>
                </div>
                <h2 id="moment-1">1. A user reports they cannot see something they expect to</h2>
                <p>
                    The most common trigger. Answering it means checking object access, field-level security, and record-level sharing, since any of the three could be the cause and the symptom looks identical regardless. <a href="/blog/salesforce-object-field-record-access.html">These three layers are explained separately here</a>.
                </p>
                <h2 id="moment-2">2. A user has access they should not have</h2>
                <p>
                    The less visible counterpart. Nobody files a ticket to report they can see something. This surfaces through incidents or spot checks, and confirming it requires the same investigation as any other access question, just triggered by suspicion rather than complaint.
                </p>
                <h2 id="moment-3">3. A scheduled or compliance-driven security review</h2>
                <p>
                    The value of a review is proportional to how completely it covers the user base, and completeness is exactly what a thirty-minute-per-user cost makes impractical at scale. <a href="/blog/how-to-run-a-salesforce-access-review.html">A full process for running one is covered here</a>.
                </p>
                <h2 id="moment-4">4. Onboarding a new hire</h2>
                <p>
                    Confirming assigned permission sets actually produce the intended access, before the first day rather than after the first complaint.
                </p>
                <h2 id="moment-5">5. Offboarding a departing employee</h2>
                <p>
                    The highest-stakes verification, since the failure mode is a departed employee retaining access with nobody left who has a reason to notice. <a href="/blog/salesforce-onboarding-offboarding-access-verification.html">What specifically to verify is covered in detail here</a>.
                </p>
                <h2 id="moment-6">6. Cleaning up permission set sprawl</h2>
                <p>
                    Before deleting a permission set that looks redundant, confirming who is assigned and what they would lose without it.
                </p>
                <h2 id="moment-7">7. Documenting an org's access model during a handover</h2>
                <p>
                    Being able to look up any user and show exactly what they can reach gives an incoming admin a concrete, checkable starting point, rather than a description that has to be taken on faith.
                </p>
                <h2 id="pattern">What is the pattern underneath all seven?</h2>
                <p>
                    Every one of these is the identical question, asked in a different context. None of the seven starts from a permission set or a profile. They all start from a person.
                </p>
