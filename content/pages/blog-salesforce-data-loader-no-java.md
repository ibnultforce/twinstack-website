                <p class="imp-text-xl imp-text-slate-600 imp-font-medium imp-mb-8">A surprising amount of Salesforce data work is blocked by a runtime.</p>
                <h2 id="the-actual-problem">The actual problem</h2>
<p>Salesforce Data Loader is a desktop application. Depending on your platform and version, it may need a Java runtime, and it definitely needs installation rights on the machine.</p>
<p>In a lot of organisations that is where it stops. Locked-down laptops, an IT ticket to install anything, a security team with a view about Java, or a Mac where the install path has changed more than once across versions. Add contractors and agency staff who need to load data but will never be granted software installation rights on a client device.</p>
<p>The result is familiar: one person in the team has Data Loader working, and every import in the company goes through that person’s laptop.</p>
<h2 id="what-that-costs">What that costs</h2>
<p><strong>A bottleneck.</strong> Loads wait for one person’s availability.</p>
<p><strong>A single point of failure.</strong> When they leave, the configured connections, the saved mappings and the scripts leave with them.</p>
<p><strong>No audit trail.</strong> Work done on a laptop is harder to reconstruct than work done inside the platform.</p>
<p><strong>Version drift.</strong> Data Loader versions track API versions. A copy installed two years ago and never updated behaves differently from a current one, in ways that are not always obvious.</p>

<h2 id="options-that-run-in-the-browser">Options that run in the browser</h2>
<p><strong>Data Import Wizard.</strong> Already in Setup, nothing to install. Limited to 50,000 records and a subset of objects, no delete, and limited lookup handling. For small loads on supported objects it is the fastest route because it is already there.</p>
<p><strong>Native AppExchange packages.</strong> A managed package installs into the org rather than onto a machine. Anyone with the right permissions can use it from any browser, and it is governed by your org’s normal access controls.</p>
<p><strong>External web-based loaders.</strong> Third-party services you connect to your org. They work, but your file is uploaded to somebody else’s infrastructure to be processed, which is a different security conversation and usually a paid one.</p>
<h2 id="what-you-give-up">What you give up</h2>
<p>Being honest about the trade: browser-based tools generally do not offer command-line automation or scheduled jobs. If you need an unattended nightly load, you need the standard Data Loader or a proper integration, and neither is a browser tool.</p>
<p>Very large volumes are also a consideration. If you are loading millions of rows in one pass, the standard loader was built for that.</p>
<p>For the everyday work, monthly account updates, list imports, migration batches in the tens of thousands, the browser option removes a genuine blocker at no real cost.</p>
<h2 id="native-versus-external-briefly">Native versus external, briefly</h2>
<p>If you do go browser-based, a native package and an external service are not the same thing.</p>
<p>A native package runs inside Salesforce. Your file is parsed and processed in your org, under your user, with your permissions. Nothing is uploaded elsewhere.</p>
<p>An external service receives your file. That may be perfectly acceptable, but it needs a security review, especially if the data includes personal information, and the review takes longer than the import would have.</p>
